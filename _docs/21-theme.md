# Theme Management

`dotfiles-theme` activates the shared application theme without copying palette values into app configs. The only available theme is `everforest-hard`.

## Topology

- `theme/everforest-hard/` is the source and mirrors paths relative to `HOME`, such as `.config/waybar/theme.css`.
- `${XDG_STATE_HOME:-$HOME/.local/state}/dotfiles-theme/bundles/` contains activation bundles. Source leaves are symlinked with the same HOME-relative paths, and each validated bundle records its theme name in a manager-owned marker.
- `${XDG_CONFIG_HOME:-$HOME/.config}/dotfiles-theme/current` atomically selects the active bundle.
- `${XDG_STATE_HOME:-$HOME/.local/state}/dotfiles-theme/active` is an advisory record written after `current`; `list` and `status` derive the authoritative active theme from `current` and its bundle marker.
- Starship and Zen files are composed from their base files plus the active theme fragments. btop, Ghostty, and Neovim selectors are generated by the manager.

`theme/` is source-only and must not be Stowed directly.

## Install

From the repository root, install the command and then the app links:

```sh
stow --no-folding -t "$HOME" theme-tools
dotfiles-theme install
```

`install` completes source, bundle, conflict, bridge, and Stow dry-run preflights before mutation. It then activates `everforest-hard`, creates stable runtime bridges, and only afterward restows the managed app packages. A runtime Stow failure can leave a partial app deployment, but every deployed loader still resolves the validated current bundle and bridges. It never uses `stow --adopt`.

Preview without changing HOME or XDG state:

```sh
dotfiles-theme --dry-run install
dotfiles-theme --dry-run set everforest-hard
```

Manage and inspect the active theme:

```sh
dotfiles-theme set everforest-hard
dotfiles-theme list
dotfiles-theme status
```

## Bridge Safety

Install accepts an exact bridge or migrates a symlink or folded ancestor only when it resolves inside this repository. It refuses plain files, foreign links, and unexpected directories, and never recursively removes app directories.

Compatibility bridges keep the previous Hyprland, Waybar, OpenCode, Brave, sysc-greet, and default Starship paths working. The Brave extension directories `${XDG_DATA_HOME:-$HOME/.local/share}/brave/themes/current` and `${XDG_DATA_HOME:-$HOME/.local/share}/brave/themes/everforest-hard` remain real directories so Chromium can safely create cache files beside the bridged manifests.

## App Selectors

- **btop:** `.config/btop/themes/current.theme` points to the packaged native `everforest-dark-hard.theme`, preferring `/usr/share/btop/themes/everforest-dark-hard.theme`. A missing native resource warns but does not block activation.
- **Ghostty:** the app config uses `theme = current`, and the bundle provides `.config/ghostty/themes/current` as a symlink to the packaged native `Everforest Dark Hard` theme. A missing native resource warns but does not block activation. Ghostty keeps its standalone opacity setting and uses app-specific GTK CSS to reduce only the tab bar's vertical height and padding.
- **Neovim:** the bundle generates `.config/nvim/theme.lua` with the Everforest colorscheme and hard background. The manager does not Stow Neovim files.
- **Starship:** `.config/starship.toml` is generated from the root palette selection, `starship/.config/starship/base.toml`, and the active palette. `${XDG_CONFIG_HOME:-$HOME/.config}/starship.toml` bridges to it so shells using Starship's default path continue working.

## Zen Profile

`install` discovers one unambiguous existing profile from supported Zen registry roots in this order: `${XDG_CONFIG_HOME:-$HOME/.config}/zen` and `$HOME/.zen`. It reads bare install-hash sections from `installs.ini`, falling back to `[Install...]` sections in `profiles.ini`, and deduplicates matching defaults. Missing or ambiguous discovery warns and skips Zen. Override discovery with an existing profile directory:

```sh
dotfiles-theme install --zen-profile /path/to/zen/profile
```

The profile receives `chrome/userChrome.css` from `zen/profile/chrome/userChrome.css`, stable `chrome/theme.css` from the active bundle, and generated `user.js`. Existing plain or foreign files are refused.

Flatpak Zen is unsupported because its sandbox cannot follow the manager's host repository, config, and state links. Automatic discovery warns and ignores a Flatpak registry; an explicit `--zen-profile` under `$HOME/.var/app/app.zen_browser.zen/` is rejected.

## Reloads

After activation, the manager may safely run `hyprctl reload config-only`, send `SIGUSR2` to exact current-user Waybar PIDs, run `swaync-client --reload-css --skip-wait`, and source `~/.tmux.conf` when a tmux server exists. Failures warn and never block activation.

btop, Brave, Ghostty, Neovim, OpenCode, existing Starship shells, and Zen may need a manual reload or restart. The manager never terminates or restarts applications.

## Greeter

Greeter synchronization is a separate privileged action:

```sh
dotfiles-theme --dry-run sync-greeter
dotfiles-theme sync-greeter
```

It copies the active sysc-greet theme once into a private snapshot, validates that snapshot, and passes its already-open byte stream through `sudo -u greeter`. Every destination-side operation runs as the unprivileged `greeter` account: it creates a same-directory temporary file, writes the validated stream, sets mode `0644`, and atomically replaces `/var/lib/greeter/.config/sysc-greet/themes/current.toml` without reopening the user-controlled source path. It does not edit preferences or caches and does not restart greetd.

After the first sync, select the custom theme named `current` once from the greeter's theme menu. Use `sysc-greet --test` for a preview. Future syncs update that selected file without another selection or a greetd restart.

## Source Audit

Run `theme-tools/tests/theme-literals.sh` from any directory to verify required artifacts, compatibility bridges, and the absence of duplicated Everforest literals in migrated app files.
